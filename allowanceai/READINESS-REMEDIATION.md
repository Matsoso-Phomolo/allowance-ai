## Financial source and API policy

- Persisted `expenses` are the authoritative source for account actual spending. Each confirmed purchase line references its one unique source expense; the immutable line snapshots reconcile to that expense. Reports must not add purchase lines to expense totals again.
- Allocations are category/month limits, plans are estimates, reserved savings are separate, and purchases are actual spending. No migration or save/evaluate action fabricates an actual expense.
- New input money: finite Decimal, up to **9999999999999999.99**, no negative/sub-cent values; endpoint rules may require strictly positive amounts. Item unit prices/quantities retain their stricter input precision. Purchase products round HALF_UP to cents. Aggregate/source historical values are retained exactly rather than destructively rounded.
- Monetary JSON fields retain their names but now return **decimal strings**. Requests accept exact strings and compatible JSON numbers; clients should send strings. Existing float-consuming external integrations require review; preserving the old lossy numeric wire representation would reintroduce R3. The bundled frontend, reports and exports are updated. Ratios/chart coordinates may use approximate numeric presentation; monetary labels/source totals remain exact.
- Backend ratio/heuristic coefficients are Decimal as well. Historical sub-cent values are displayed with their meaningful extra digits; new writes reject those values. Currency preference changes presentation only, never stored currency/amounts.
- Manual create retries are deduplicated only when the caller supplies the same `operation_key` and semantic input. The bundled UI retains the saved operation after unknown outcomes; known validation/conflict rejections allow correction. Repeated intentional creates with different keys remain distinct operations.

## Schema/migration changes

- **0001_legacy:** strengthened adoption checks; a truly empty schema is created, a complete compatible legacy schema is adopted, partial/incompatible schemas are rejected. No implicit ownership repair or version stamp workaround.
- **0002_item_ledger:** retains the reviewed NUMERIC conversion and five item-ledger tables; runs baseline validation before conversion. These revisions remain uncommitted/unreleased in this repository. If any environment has applied another copy, compare its migration history and frozen definitions before release; never silently rewrite an externally applied history.
- **0003_month_allocations:** additive `category_allocations` and `expense_operations` tables. Snapshots old category limits to known user budget/expense months (current month only for an undated account) with `origin=legacy_snapshot`; source categories, budgets, expenses, password hashes, account IDs and purchase history remain unchanged. No assertion that a copied shared value was the true historical monthly allocation.
- Later explicit month edits affect only that month. A category absent from a month's allocations has zero unconfigured allocation, not a fallback to the archived shared value. Category identity/names remain shared user-owned taxonomy; changing its name is not changing every month's amounts.
- Runtime PostgreSQL requires exactly one `0003_month_allocations` revision. Test schema creation remains test-only. Unknown/multiple heads and drift fail without dropping or restamping history. All destructive downgrades remain blocked.

## Outstanding risks and gates

- **Blocking external evidence:** actual Neon schema/history and identity inspection is pending access; the production backup/restore rehearsal and migration lock timing have not been performed. Therefore the final production recommendation remains **NO-GO**, regardless of successful local fixes.
- Baseline adoption intentionally rejects incompatible nullability/types/foreign keys/indexes/sequence states instead of guessing repairs. An encountered legacy difference requires a separately reviewed data-preserving repair/adoption plan.
- Legacy monthly limits were never historically snapshotted. Their migrated values are explicitly inferred legacy snapshots; true historical per-month allocations cannot be recovered from nonexistent data.
- Monetary strings are a deliberate exactness contract change for old integrations. Large/old sub-cent values must not be coerced back to float by external clients. Old clients without operation keys do not receive create-retry deduplication guarantees.
- Confirmed purchase correction/reversal remains unsupported; immutable history is preserved. Handle mistakes through an approved audited adjustment/forward-repair process, not manual deletion. No reversal feature was added by this remediation.
- Session recovery survives refresh in the current browser tab/session; clearing browser storage or ending the session requires checking server history before a new operation. Cross-device unknown-outcome recovery needs a support procedure. No full load test, physical-device accessibility certification or per-user time-zone accounting is claimed.
- Existing all-history list serialization/rebuild cost remains a scale consideration. Database pre-ping/recycle/connect timeout is configured, but production Neon pool/role/TLS behavior and bounded failure handling still need the staging/provider rehearsal.
